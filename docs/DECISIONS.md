# 로그 재처리 설계 판단

고정된 로그 파일을 재처리할 때 서비스 지표가 달라지지 않도록 저장과 조회의 기준을 정했다. 복구 정확성을 먼저 검증하고, 처리량과 분산 처리는 후속 과제로 둔다.

| 질문 | 선택 | 비용과 남은 문제 |
| --- | --- | --- |
| 재시작 후에도 같은 이벤트를 구분하려면 | DB에 (service, event_id) 고유 키 저장 | 메모리 set만 사용하는 후보와 달리 저장 상태가 유지된다. DB 접근 비용이 든다 |
| 지표를 언제 계산할지 | 커밋된 events에서 SQL 조회 | 별도 카운터의 이중 증가를 피한다. 조회마다 집계 비용이 든다 |
| 어디부터 재시작할지 | 원본을 처음부터 다시 읽기 | 진행 위치와 저장 상태를 함께 관리할 필요가 없다. 재처리 시간이 입력 크기에 비례한다 |
| 같은 ID의 다른 내용을 처리할지 | 첫 유효 이벤트 유지, 새 입력 격리 | 조용한 덮어쓰기를 막는다. 첫 값의 정확성을 보장하지 않으며 자동 정정이 필요할 수 있다 |
| 오류 파일과 DB를 함께 갱신할지 | 오류도 DB에 기록하고 별도로 내보내기 | 트랜잭션으로 복구 상태를 묶는다. 오류 내보내기 명령이 추가된다 |
| 각 행을 즉시 커밋할지 | 기본 100줄씩 묶어 커밋 | 커밋 횟수가 줄어든다. 중간 종료되면 미완료 묶음을 다시 처리해야 한다 |
| 시간대를 유연하게 받을지 | v1은 UTC 고정 형식만 허용 | 시간대 보정으로 의미가 바뀌지 않게 한다. 다른 형식은 명시적으로 거부한다 |

위 대안 중 메모리 set 수집기, 별도 집계 카운터, 진행 위치 저장 방식은 구현 비교 실험을 수행하지 않은 설계 후보다. 배치 크기 1, 4, 100의 최종 결과 일치는 검사했지만 성능 우열을 측정한 결과로 쓰지 않는다.

## 검증에서 발견한 문제

출력 경로를 DB 경로와 같게 지정하면 원자적 파일 교체가 정상 DB까지 덮어쓸 수 있었다. report와 rejects 두 명령에 대한 실패 테스트를 먼저 추가했고 두 테스트가 실제 실패했다. 출력 경로 충돌을 검사하는 보호 로직을 추가한 뒤 모두 통과했다.

Windows 검증에서는 테스트가 DB 조회 연결을 명시적으로 닫지 않아 임시 DB 정리에 실패했다. SQLite 연결의 with 문은 트랜잭션을 관리하지만 연결 종료를 대신하지 않는다. 검증 도구의 연결을 명시적으로 닫아 Windows 테스트를 통과시켰다. 애플리케이션의 DB 연결 종료와 검증 도구의 연결 종료를 구분해 확인했다.

## 다음에 검토할 문제

파일 크기가 커지면 전체 재처리 비용을 측정하고 진행 위치 저장이 필요한지 판단한다. 진행 위치를 도입할 때는 이벤트 저장과 같은 트랜잭션으로 묶는 구조를 검토한다. ID 충돌은 서비스별 정책과 정정 이벤트를 정의해야 자동 해결할 수 있다. 다중 수집자를 지원하려면 SQLite 쓰기 직렬화, 소유권과 재시도 정책을 별도로 설계해야 한다.
